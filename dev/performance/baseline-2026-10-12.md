# Local idle baseline, 2026-10-12

This is an empty-lobby measurement, not a player-capacity or client-FPS result.

The test ran the feature code from `7b5c54a` plus the map readiness command on Windows 11, an Intel i5-13600KF
with 20 logical processors, Temurin 25.0.4.1, and Paper 26.2 build 133. The JVM used `-Xms512m -Xmx1g`.
BlockcraftAPI, BlockcraftCore, Lobby, and LuckPerms 5.5.82 were loaded. MariaDB ran locally on port 3307
with a disposable schema. The server bound to `127.0.0.1:25576` and stopped after the recording.

The world was a generated flat test map, with view and simulation distances of four, no players, no configured
activity positions, and empty-server pausing disabled. Spark and bStats were disabled. After startup and 30 seconds
of warmup, `jfr start` recorded 90 seconds before `jfr stop` and `mspt`.

| Measurement | Result |
|---|---:|
| JFR tick-window samples | 86 |
| Mean tick-window average | 0.115 ms |
| p95 tick-window average | 0.160 ms |
| Maximum tick-window average | 0.321 ms |
| Mean JVM CPU, normalized across the machine | 0.323% |
| Paper `mspt`, last minute average / maximum | 0.1 / 0.9 ms |
| GC pauses at recording boundaries | 79.2 ms and 61.8 ms |

Both GC events reported `Heap Inspection Initiated GC`. Their timestamps match recording start and stop.
They are profiler overhead in this capture, not evidence of a recurring gameplay GC problem. The JFR summary's
percentiles use the nearest-rank method; Minecraft's own generated report can use a different method.

The raw recording and log remain locally under `run/performance/server/debug/server-2026-10-12-225952.jfr`
and `run/performance/controlled-server.log`. Reproduce the summary with:

```powershell
python dev/performance/summarize.py jfr run/performance/server/debug/server-2026-10-12-225952.jfr
```

Startup also produced six existing leaderboard query failures because the lobby-only database had no game stats
tables. The current lobby refresh queries those boards even when no holograms are placed. A follow-up can restrict
queries to placed boards and handle game tables that have not been created yet. This measurement does not establish
the CPU or database benefit of that change.

The runtime readiness check reported all 13 expected setup problems on the empty map. No client connected, so the
capture does not validate rendering, gameplay, proxy forwarding, or performance under player load. Use the
[capture workflow](README.md) with the real map and representative players before setting a capacity target.
